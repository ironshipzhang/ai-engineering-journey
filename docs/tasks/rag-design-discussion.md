## 已讨论的关键概念

### 状态事实、规则与证据不足

虚构场景：精确查询返回“星桥数据库迁移失败”，发布规范和迁移手册提供发布条件与处理要求。已有 project_id 的状态查询继续适合精确工具；非结构化规范可以通过检索提供适用章节。少量短文档直接放入上下文也合理，RAG 并非回答问题的必要前提，但具有机制学习价值。

用户明确判断：没有找到适用发布规范时，不能仅由“迁移失败”推导出“禁止发布”；应报告已有事实、说明未找到规范，可以建议人工确认。RAG 提供候选证据，不能自动保证答案正确；引用存在也不等于引用支持结论。

### 原始文档与派生数据

原始文档由人维护，例如《发布规范》中的迁移条款。切分后的片段文本、片段向量、来源章节和版本关联等是派生数据，可按原始资料与处理配置重新生成。Toy 可以用文件与内存组织这些记录，不因使用“索引”就必须部署数据库服务。

索引类似缓存或物化视图：原文变化不意味着派生数据自动同步。片段文本变化时，其向量需要相应更新；原文删除后旧片段也应退出检索；更换不兼容的 embedding 模型通常需要重建文档向量，查询编码必须与索引兼容。

### 索引生命周期

生命周期覆盖：发现变化 → 确定更新范围 → 构建派生数据 → 校验 → 切换可用版本 → 清理旧数据，以及失败恢复与过期处理。

- 自动发现：文件事件监听、定期扫描并比较内容指纹、数据源事件通知。事件可能重复、延迟或遗漏，可合并连续事件并用定期核对补偿；不是收到事件就必然得到一致索引。
- 文档级增量：只重新切分和编码发生变化的文档，替换它的旧片段，其余文档保持不变。
- 片段级增量：比较片段内容和编码配置，复用兼容且未变的向量，生成新增或修改的向量，删除消失片段。切块边界可能因少量文本修改而整体移动，不能假设一句修改只影响一个片段。
- 版本切换：先准备并校验新版本，再使查询使用它，避免查询读到新旧混合或半成品；构建失败时不应把新版本标为可用。具体切换机制取决于存储方案。
- 工程问题：重复更新的幂等性、更新中再次修改、删除传播、索引新鲜度、重试和监控。是否允许暂用旧索引需由业务决定；权限撤销不能简单沿用一般内容更新的宽松策略。

以上是概念和设计模式说明，不代表这些机制已实现或选定了特定产品。

## 共识、候选方案与取舍

- 用户接受 Toy 使用全量重建的简化方向，要求明确标识这种简化；求职项目需要再设计更完整的工程方案。
- 全量重建逻辑简单、便于观察删除与版本变化，但可能重复处理未修改资料。建议 Toy 手动触发，记录文档指纹与编码配置，发现过期时提示重建；具体校验时机和失败行为仍待确认。
- 自动监听、增量更新、后台同步、幂等恢复和监控延后到求职项目评估。完整方案应由数据规模、更新频率、允许延迟和权限需求驱动，不预先承诺所有机制都必须实现。
- 检索工具返回片段与来源，最终由 Agent 综合状态和资料回答；文档是参考数据，不是执行指令。检索分数不能解释为答案正确率。
- 尚未选择 embedding 模型/API、本地运行库、存储格式或检索算法；不能默认现有 DeepSeek 生成接口也提供所需 embedding 能力。

## E1–E3 的建议范围

拆分来自 docs/toy-agent-progress.svg。以下细化是讨论建议，主会话仍需将其收敛为逐项任务和验收标准。

| 子任务 | 解决的问题 | 建议边界 |
| --- | --- | --- |
| E1：文档、切块、来源与索引生命周期 | 准备可追踪、可更新的检索资料 | 数份虚构规范/手册，定义文档与片段标识、章节、版本及过期判断；明确全量重建策略。实际向量构建放在 E2。 |
| E2：embedding、检索与有来源的回答 | 找到适用证据并据此回答 | 先独立观察 query 的候选片段，再组织上下文和生成回答；采用固定检索流程作为候选起点，区分无结果、错误结果和生成错误。 |
| E3：接入工具注册表，记录检索轨迹 | 让现有 Agent 使用并暴露检索过程 | 将检索封装为只读工具，模型提供 query，程序校验并执行，返回片段与来源；记录查询、命中标识与索引版本，并检查与当前 Loop 边界的兼容性。 |

E3 不能将“工具调用成功”直接等同于“证据足够”：空结果可以是正常检索结果，有结果也可能不适用。新任务的完成条件、证据不足表达和引用结构需另行设计，不直接套用当前三字段摘要契约。用户对 E3 的基本调用过程已无额外问题。
