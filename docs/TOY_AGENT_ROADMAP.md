# Toy Agent 完整学习路线

更新时间：2026-10-12。此路线描述计划，不代表未来功能已实现。

目标：能解释并演示模型调用、工具执行、有界循环、任务状态、检索、MCP 和评估之间的关系。使用小规模虚构数据学习机制；业务内容质量优化留到有实际需求与数据的后续工程项目。

## 已完成

- Python / uv / VS Code / Git 环境与 API 调用。
- 三字段结构化摘要与本地格式校验。
- 单个只读 get_project 工具、参数校验与消息 ID 绑定。
- 最多 5 次模型请求的 Loop、任务内成功缓存与异常停止。
- 小型摘要评估、版本比较与三维内容验收方法；本阶段练习结束。
- 任务 C：结构化运行结果、失败轨迹与 CLI JSON 保存。
- 任务 D / D2：多项目输入、两种只读任务与 Tool Registry，支持单轮 1～2 个调用整批校验后顺序执行；已通过主会话验收，71 项离线测试通过，一次真实 issues 双工具任务成功。

结构化运行结果与执行轨迹已通过主会话机制验收，39 项离线测试通过；用户正常两轮运行和 --output JSON 保存均已验证，异常与文件失败路径仍仅离线验证。内容评估方法已掌握，停止继续调优；历史结论归档，不阻塞后续学习。

## 后续顺序

1. **任务状态、结果与执行轨迹（已完成）**：返回成功/失败、摘要、已知用量、请求次数和工具事件；失败仍保留已有记录。39 项离线测试通过，正常真实运行与 JSON 保存验证完成。
2. **多项目输入与 Tool Registry（D / D2 已完成）**：JSON 每任务快照，默认 xingqiao / summary，支持 issues；get_project 与 list_project_issues 通过显式注册表关联 schema、校验和执行。按任务检查必要结果，缓存隔离工具与参数；单轮最多两个调用，整批校验后顺序执行。71 项离线测试通过，真实 summary 与一次 issues 双工具成功已记录。详见 [任务 D 交接](tasks/multi-project-registry.md) 与 [D2 交接](tasks/two-tool-batches.md)。
3. **最小 RAG**：用数份虚构文档，完成切块、embedding、存储、检索、上下文注入与来源标识；对比命中与未命中。先明确 embedding 来源和成本，再实现；不要求向量数据库服务。
4. **最小 MCP 接入**：将一个已理解的只读工具放入本地 MCP Server，由 Agent 的 MCP Client 调用；保持直接调用路径用于比较。SDK、传输和依赖在开工时核实。
5. **失败策略与安全边界**：基于当前失败停止机制，补充分类、只读幂等请求的有界重试与等待策略；判断超时的不确定性。限流/余额不盲目重试，fallback 不伪造成功；用离线异常验证，不以真实故障练习。
6. **端到端评估**：复用运行轨迹，在少量完整任务上检查正确取数、工具选择、停止、检索来源、格式与内容；对独立样例及必要重复采样控制预算。每新增机制先局部测试，不等到最后才验证。
7. **CLI 演示与学习验收**：统一项目/任务输入、结果文件、配置、安装运行说明与失败演示；保存一个可复现的 Git 版本，能解释取舍和边界。

可选：一个明确任务流程的 Skill 概念验证（先定义与 Tool/Prompt/Workflow 的区别）；流式输出体验。是否实现按学习价值决定，不阻塞收尾。

## 收尾边界

完成一条可演示的只读任务链：输入任务 → 获取业务状态和检索资料 → 通过工具/MCP 执行 → 输出有来源的结果与轨迹 → 评估与失败说明。不是生产系统，不要求内容百分百正确。

真实业务质量、写操作与审批、企业权限、服务化、部署和生产运行，进入后续 Product Operations 工程项目。仍保留 Go 后端优势，不在 Toy 中扩建完整运营平台。

每次只实现一项独立任务，主会话设计与复核，子会话编码；路线可随实际学习结果调整。
