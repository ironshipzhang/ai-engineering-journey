# 发布后检查清单

本文是学习项目的虚构资料，版本为 1，描述模拟运营平台完成一次常规发布后的观察和记录。它只关注发布后检查，不证明发布前条件已经满足，也不补充其他发布类型的审批制度。检查结论必须关联具体环境、应用版本及本次变更范围。

## 开始观察

开始检查前，记录发布完成时间、实际部署版本、配置版本和观察窗口。确认请求确实进入新版本实例，不能仅看到部署命令返回成功就结束观察。若仍存在旧实例，应记录分布情况并确认是否符合计划，不能把混合版本下的结果归因于单一版本。

观察窗口内应保留检查时间和证据位置，避免只留下“目前正常”的结论。没有观察到错误与没有发生错误不是同一回事；如果流量不足、指标缺失或检查尚未完成，应明确记录限制，不把空白监控面板解释为已经通过。

## 服务和接口检查

检查服务健康状态、关键接口响应、错误日志及延迟变化，优先覆盖本次变更影响的路径。对模拟写入流程使用专门的虚构测试数据，并记录是否执行了清理。只读接口成功不能代表写入流程正常，单个健康检查通过也不能代表全部业务功能可用。

发现异常时应记录首次出现时间、受影响范围及与旧版本的比较证据，暂停扩大变更范围并按照已有方案处理。尚未排除其他因素前，不把时间上的接近直接表述为“本次发布必然导致故障”。诊断结论需要与实际日志和验证结果对应。

## 数据库相关检查

涉及数据库变更时，核对应用实际使用的结构与目标迁移版本是否一致，检查关键读写路径以及数据约束。此处是发布后的观察，不能替代发布前迁移验证；即使当前请求成功，也不能据此补记先前缺失的验证记录。

如果发现迁移状态不一致或怀疑部分执行，应保存当前证据并参照《数据库迁移手册》开展排查。不得为了快速消除告警而反复运行迁移脚本，也不得直接改写版本记录。恢复方案需要覆盖真实执行状态，在练习中应记录尚缺哪些确认步骤。

## 恢复观察与结束记录

若执行恢复操作，应分别检查应用版本、数据库状态和关键接口，不把恢复命令成功等同于业务恢复。观察到的异常即使暂时消失，也应记录持续观察的时间和范围。没有证据证明原因已消除时，应保留后续检查项和结论的不确定性。

最终记录包括已完成检查、未完成检查、异常处置和遗留问题。结论应限定在实际覆盖的环境和窗口内，不能扩大为长期稳定承诺。后续人员可根据记录继续观察；需要其他规则依据的问题，应另行查找适用资料并说明当前证据的边界。
