# 数据库迁移手册

本文是学习项目的虚构资料，版本为 1，用于解释模拟运营平台的迁移排查步骤。它不包含真实数据库地址、账号或可执行的生产脚本。迁移是否满足某次常规发布的条件，应结合《发布规范》和该次验证记录判断；本手册不证明任何项目当前已经恢复。

## 执行前的记录

模拟迁移前应记录环境标识、脚本版本、预期结构变化和数据检查方式，确认备份及恢复方案对应同一目标。脚本评审需要明确事务边界和重复执行的影响。不能因为 SQL 文件较短，就默认其中所有语句会同时成功或同时回滚。

执行过程应保留开始与结束时间、工具返回结果及日志位置。网络连接中断或客户端超时，只说明客户端没有取得完整结果，不能直接证明数据库没有执行。保留这些不确定性有助于后续核对，不应把超时记录自动改写成“零变更”。

## 失败后重跑前的检查

迁移失败或结果不明时，先暂停自动重跑，按以下顺序收集并核对证据。三个检查项共同用于判断执行状态，不能只完成其中一项就直接重新运行：

1. 检查执行日志，定位失败语句、错误信息和最后确认成功的位置；同时检查是否存在日志缺失或客户端超时。
2. 检查迁移版本记录，比较记录中的版本、成功标记和目标脚本；版本记录只能作为一项证据，仍需核对实际结构和数据。
3. 确认是否发生部分执行，核对相关表、字段、约束及数据变化；日志、版本记录或实际状态相互矛盾时，将结果记为无法确认。

只有完成上述检查，确认执行状态，并验证重跑方案对该状态安全后，才考虑重新执行。发现部分执行或无法确认状态时，不得直接重跑原脚本；应先制定恢复或修复方案并验证。即使确认没有发生变更，也仍需排除失败原因和验证脚本，不以“没有变更”单独作为重跑依据。

## 恢复与重新验证

恢复方案应明确要修复的对象、保留的数据及可能影响的关联约束。不能简单删除迁移版本记录来伪装为未执行，也不能假设应用 rollback 会恢复数据库。数据恢复与应用回退需要分别核对其前提，未经验证的恢复方案保持为待办状态。

修复或重新执行后，应再次检查迁移版本记录、结构变化及关键数据，保存新的结果。只有新的验证证据才能支持“本次迁移验证通过”。旧失败日志继续保留并关联修复记录，不能通过覆盖旧日志消除失败历史。

## 排查交接

交接时应区分已确认事实、推测原因和未完成检查，说明暂停位置及下一步需要的证据。交接材料不包含密钥或真实业务数据；练习中仅使用虚构标识。接手人员应先核对环境与脚本版本，避免对错误目标执行计划中的操作。
